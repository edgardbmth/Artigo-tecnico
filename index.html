Quando a redundância controlada é a chave para a alta performance de leitura.

1. O Problema Real: A Lente do JOIN em Grandes Volumes

Normalizar um banco de dados é excelente para evitar anomalias e duplicidade em operações de escrita (INSERT, UPDATE, DELETE). No entanto, em um dashboard financeiro que precisa calcular diariamente o total vendido por milhar de clientes, fazer JOIN entre 5 tabelas com milhões de linhas torna o sistema lento e consome CPU desnecessária.

O Custo do Excesso de Normalização:

Consultar pedidos → itens_pedido → produtos → clientes gera varreduras pesadas em disco. Quando o volume cresce, relatórios simples começam a demorar segundos ou até minutos para carregar.

2. O que é Desnormalização? (OLTP vs OLAP)

Desnormalizar é introduzir redundância planejada e controlada no banco de dados para otimizar o tempo de resposta das consultas de leitura (READ).

Sistemas OLTP (Transacionais)

Focados em escrita rápida, consistência máxima e baixa redundância (Normalizado em 3FN).

Sistemas OLAP (Analíticos)

Focados em leitura e relatórios pesados. Utilizam dados pré-agregados e tabelas achatadas (Esquema Estrela / Desnormalizado).

3. Principais Técnicas de Desnormalização

  • Colunas Derivadas / PRÉ-Calculadas: Adicionar uma coluna total_pedido diretamente na tabela pedidos em vez de somar os itens a cada consulta.
  • Tabelas Achatadas: Juntar dados de clientes e pedidos na mesma estrutura para relatórios sem necessidade de JOIN.
  • Views Materializadas: Armazenar o resultado de uma consulta complexa em disco e atualizá-la periodicamente.

4. Comparando Desempenho na Prática (PostgreSQL)

Abaixo demonstramos o contraste entre consultar os dados reconstruindo os JOINs e utilizar uma View Materializada desnormalizada.

PostgreSQL 15+ | 01_desnormalizacao_e_views.sql Ver no GitHub 
-- 1. Consulta Normalizada (Exige múltiplos JOINs)
EXPLAIN ANALYZE
SELECT c.nome, SUM(ip.quantidade * ip.preco_aplicado) AS total_gasto
FROM clientes c
JOIN pedidos p ON c.id_cliente = p.id_cliente
JOIN itens_pedido ip ON p.id_pedido = ip.id_pedido
GROUP BY c.nome;

-- 2. Criando uma Tabela/View Desnormalizada para Relatórios
CREATE MATERIALIZED VIEW mv_relatorio_vendas_cliente AS
SELECT c.id_cliente, c.nome AS cliente_nome, SUM(ip.quantidade * ip.preco_aplicado) AS total_gasto
FROM clientes c
JOIN pedidos p ON c.id_cliente = p.id_cliente
JOIN itens_pedido ip ON p.id_pedido = ip.id_pedido
GROUP BY c.id_cliente, c.nome;

-- 3. Consulta Achatada (Sem JOIN - Resposta Instantânea)
EXPLAIN ANALYZE
SELECT cliente_nome, total_gasto FROM mv_relatorio_vendas_cliente;

5. Os Perigos da Redundância e Como Manter a Consistência

Cuidado: Desnormalizar sem controle introduz o risco de dados inconsistentes! Se a coluna desnormalizada não for atualizada em sincronia com os dados primários, relatórios tomarão decisões baseadas em números errados.

Como resolver? Utilize Triggers automáticas para atualizar totais derivados ou programe atualizações agendadas (Cron) para atualizar as Views Materializadas (REFRESH MATERIALIZED VIEW).
